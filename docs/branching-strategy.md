# 브랜치 전략 & PR 규칙

이 문서는 `gitops` 레포에서 브랜치를 어떻게 나누고, PR을 어떻게 처리하는지 정의합니다.

## 브랜치 구조

이 레포는 `main`과 `feat/*`(작업 브랜치) 2단계만 사용합니다. 서비스 소스코드 레포(`sever` 등)와 달리 `dev` 브랜치를 두지 않습니다.

- **`main`**: 항상 배포 가능한 상태. ArgoCD가 이 브랜치를 직접 감시(`targetRevision: main`)하고 있어, 여기 반영된 내용이 곧 클러스터의 실제 상태입니다.
- **`feat/기능이름`**: 작업 단위 브랜치. 예: `feat/kafka-cronjob-template`, `feat/eso-secret-binding`. 작업이 끝나 PR로 merge되면 삭제합니다.

`fix/`, `chore/` 같은 접두사도 필요에 따라 자유롭게 사용합니다(강제 규칙 아님).

## main과 배포의 관계

`gitops` 레포의 ArgoCD Application들은 전부 `syncPolicy.automated: {prune: true, selfHeal: true}`로 설정되어 있습니다. 즉 **`main`에 merge되는 순간 ArgoCD가 자동으로 클러스터에 반영합니다** — 별도의 배포 태그나 수동 승인 단계는 두지 않습니다.

- 이건 GitOps 자동동기화의 기본 동작 방식을 그대로 따르는 것으로, 의도적인 선택입니다.
- 실수 방지 장치는 배포 시점이 아니라 **PR 단계**에서 겁니다 (아래 PR 규칙 참고).
- 참고: `sever` 등 서비스 소스코드 레포는 이것과 다른 정책(merge와 실제 이미지 배포를 분리하는 배포 태그 방식)을 쓸 수 있습니다 — 이건 이 문서의 범위가 아니라 각 소스코드 레포에서 별도로 정합니다.

## PR 규칙

- **PR 필수**: `main`에 직접 push 금지, 반드시 `feat/*` 브랜치에서 PR을 통해서만 반영
- **승인 인원**: 현재 0명 (인프라 담당자 혼자 다루는 레포이기 때문). **팀원이 합류하면 최소 1명 승인 필수로 재검토합니다.**
- **Merge 방식**: Squash merge — `feat/*` 브랜치의 여러 커밋을 하나로 합쳐서 `main`에 반영, 히스토리를 깔끔하게 유지
- **CODEOWNERS**: 현재 미사용 (혼자 다루는 레포라 실익이 적음). 팀원이 합류해 담당 영역(예: addon vs 서비스 values)이 나뉘면 재검토합니다.
- **PR 템플릿**: 현재 없음. 다른 4개 레포(`ai`/`mobile`/`web`/`sever`)엔 이미 있으므로, 필요 시 그 형식을 참고해 추가합니다.
